# Nest vs Spring 개념 정리 (I/O, CPU, 구조/생태계, MQ 쓰임새)

벤치마크 결과를 해석하기 위해 대화로 정리한 개념 문서다.
- 이 문서의 내용은 **일반적인 경향**이며, 이번 프로젝트에서 측정한 값이 아니다.
- 측정 결과는 `reports/scale-result.md`를 본다.

## 1. I/O 작업은 Node와 Spring 중 어느 쪽이 유리한가

흔한 오해는 "멀티스레드라서 I/O도 Spring이 낫다"는 것이다. 일반적으로는 반대에 가깝다.

| | Node (NestJS) | Spring (JVM) |
|---|---|---|
| 실행 모델 | 단일 스레드 이벤트 루프 + 논블로킹 비동기 I/O | 멀티스레드 (기본 Spring MVC는 요청당 스레드, 블로킹 I/O) |
| I/O 대기 중 | 스레드가 놀지 않고 다른 요청을 처리한다. | 스레드가 대기 상태로 묶인다. |
| 유리한 작업 | I/O 대기가 많은 작업, 동시 연결이 많은 서비스 | CPU를 오래 쓰는 복잡한 연산, 멀티코어 활용, 장시간 지속 처리량 |
| 약한 작업 | CPU를 오래 쓰는 작업은 이벤트 루프를 막아 다른 요청이 밀린다. | 동시 요청이 많은 블로킹 I/O는 스레드 수와 컨텍스트 스위칭 비용이 부담이다. |
| 기동과 메모리 | 가볍다. | 상대적으로 무겁고 JIT 워밍업이 필요하다. |

- Spring도 논블로킹으로 쓸 수 있다. **WebFlux**나 Java 21의 **가상 스레드**를 쓰면 블로킹 I/O의 약점이 많이 줄어든다.
- 이 프로젝트의 Spring은 기본 MVC에 일반 스레드를 쓴다.
- Node에서 CPU 작업이 필요하면 `worker_threads`나 cluster, 또는 별도 서비스로 분리한다.

## 2. 이 벤치마크의 작업 성격

- 컨슈머가 하는 일: JSON 파싱(CPU, 가벼움) + MQ 송수신(I/O) + DB INSERT(I/O).
- DB 풀이 10개이므로 DB 저장이 들어가는 시나리오는 DB가 병목이다. 이때 앱 간 차이는 작게 나올 가능성이 크다.
- DB 저장이 없으면 메시지 처리 자체가 병목이라 앱 차이가 더 드러날 수 있다(현재 시나리오는 모두 DB 저장 O).
- 메시지당 CPU 작업(`cpu=N`)을 넣으면 CPU 중심 상황에서의 차이를 확인할 수 있다. 아직 구현하지 않았다.

## 3. 메시지가 많으면(천 건, 만 건, 수백만 건) Spring이 더 빠른가

"엔터프라이즈에 유리하다"와 "메시지 건수가 많으면 빠르다"는 다른 이야기다.

- 천~만 건: 둘 다 1초 안팎에 끝난다. JIT 워밍업 같은 노이즈가 커서 앱 차이를 보기 어렵다.
- 수백만 건: 장시간 지속 처리량이 중요하다.
  - JVM: 워밍업 후 안정적이고 멀티코어를 쓴다. GC와 힙 튜닝이 필요하다.
  - Node: 코어 하나만 쓰므로 인스턴스를 여러 개 띄우거나 cluster 모드로 확장한다.
- 병목이 DB나 브로커이면 앱 차이는 가려진다. (측정: 규모를 키워도 처리량이 1만~10만 건부터 평탄해지는 것은 DB 풀 10과 4코어 CPU 한계 영향으로 보인다)
- 따라서 "대규모면 Spring이 낫다"는 성능 법칙이 아니다. 작업 성격과 병목에 달려 있다.
- 현재 데이터는 최대 10,000건이다. 수백만 건에 대한 결론은 낼 수 없다.
  - 확인하려면 100,000건 이상 시나리오가 필요하다. 지금은 지연 값을 메모리에 쌓기 때문에 수백만 건은 수정이 필요하고, 10만~100만 건이 현실적이다.

## 4. 구조와 생태계

### 구조
- 계층 분리(Controller, Service, Repository), 의존성 주입(DI), 관례 중심의 설정과 폴더 구조.
- 코드가 커져도 어디에 무엇이 있는지 예측하기 쉽고, 새 팀원이 읽는 비용이 낮다.
- 이 프로젝트에서도 Spring은 어노테이션과 DI(`@KafkaListener`, `JdbcTemplate`), Nest는 `@Module`, `@Injectable`, `@Controller`로 비슷한 구조를 만들었다. 구조 면에서 Nest는 Spring과 거의 대등하다.

### 생태계
- **Spring:** 트랜잭션, 보안(Spring Security), 배치(Spring Batch), 스케줄링, 모니터링(Actuator), 클라우드 연동이 하나의 체계로 제공된다. Kafka, RabbitMQ, Redis, DB용 starter가 공식 지원이며 설정만으로 자동 구성된다.
- 20년 넘게 대규모 서비스에서 검증되어 장애 사례, 튜닝 문서가 많다.
- 금융, 대기업 SI 등에서 Java/Spring 인력이 많아 유지보수 인력을 구하기 쉽다.
- **Node:** npm 패키지가 많고 신기술 채택이 빠르다. 대신 패키지 품질이 들쭉날쭉하고 조합할 부분이 많다. (예: kafkajs는 2024년 중반 이후 커밋이 거의 없다.)

### 결론
"엔터프라이즈에 유리하다"는 큰 시스템을 오래 여러 사람이 유지보수할 때의 안정성, 검증된 공식 도구, 인력 수급의 이점이다. 같은 서버에서 초당 몇 건을 처리하는지와는 별개다.

## 5. CPU를 많이 쓰는 작업과 주로 쓰는 기술

### CPU 중심 작업의 예
- 데이터 가공과 계산: 대량 집계와 통계, 큰 JSON/XML/CSV 파싱, 정렬과 매칭, 금융 계산
- 암호화와 보안: 비밀번호 해시(bcrypt, argon2는 일부러 CPU를 오래 쓰게 만든 알고리즘), 암호화와 복호화, 서명 검증
- 미디어와 파일: 이미지 리사이즈, 동영상과 오디오 인코딩, 압축, 대용량 PDF/엑셀 생성
- 알고리즘성 작업: 추천 점수, 랭킹, 검색 인덱싱, 텍스트 분석, 최적화, 간단한 ML 추론

### 주로 쓰는 쪽
| 작업 | 많이 쓰는 쪽 | 비고 |
|---|---|---|
| 대량 집계, 정산, 배치 | Spring(Java), Spring Batch, Spark | 금융, 통신, 대기업 정산 |
| 금융 계산, 위험도 계산 | Java/Spring, C++ | 초저지연 구간은 C++ |
| 암호화, 보안, 인증 | Spring Security(Java), Go | |
| 이미지, 동영상, 음성 | Python, C/C++ (ffmpeg, libvips 호출) | 무거운 계산은 네이티브 라이브러리가 하고 앱은 호출한다. |
| ML, 추천, 데이터 분석 | Python (FastAPI, Django + NumPy, PyTorch) | 계산은 C/CUDA 라이브러리가 한다. |
| 검색, 텍스트 분석 | Java(Lucene, Elasticsearch), Python | |
| 고성능 서버, 동시성 마이크로서비스 | Go, Rust | |
| I/O 중심 API, 실시간(채팅, 알림) | Node(Nest, Express) | |

- 실무에서는 한 프레임워크로 다 하기보다, 메인 API는 Spring이나 Nest로 두고 무거운 계산만 별도 워커나 서비스(Python, Go 등)로 분리하는 구성이 흔하다.

## 6. MQ는 어느 분야에서 많이 쓰나
MQ가 무엇인지, 세 MQ의 구조와 장단점은 `docs/mq/`(MQ란, Redis Streams, RabbitMQ, Kafka)에 정리했다.

### 분야별
| 분야 | 주로 쓰는 MQ | 이유 |
|---|---|---|
| 대규모 이벤트 스트리밍(로그, 클릭, 행동 데이터) | **Kafka** | 처리량이 높고 메시지를 보관해서 재처리할 수 있다. |
| 데이터 파이프라인(CDC, 데이터 레이크, 실시간 분석) | **Kafka** | Debezium, Spark, Flink 생태계와 연결된다. |
| 금융, 결제, 주문 같은 이벤트 기반 MSA | **Kafka**, RabbitMQ | 순서와 보관이 중요하면 Kafka, 작업 분배와 라우팅이 중요하면 RabbitMQ |
| 작업 큐(메일, 알림, 이미지 처리, 백그라운드 작업) | **RabbitMQ**, Redis 기반 큐(BullMQ 등) | 라우팅, 재시도, 우선순위가 필요하고 처리량은 크지 않은 경우가 많다. |
| 가벼운 비동기 처리, 이미 Redis를 쓰는 소규모 서비스 | **Redis Streams** | 별도 브로커 없이 쓸 수 있고 운영이 간단하다. |
| 실시간 알림, 채팅 | Redis(Pub/Sub, Streams), RabbitMQ | 낮은 지연 |

### 프레임워크와 환경별
- **Spring 환경:** Kafka가 가장 흔하다. 대기업과 금융권 MSA에서 Kafka + Spring 조합이 많고, RabbitMQ도 오래 쓰였다. `spring-kafka`, `spring-amqp`가 공식 지원이다.
- **Node(Nest) 환경:** 중소규모와 스타트업에서 RabbitMQ나 Redis(BullMQ) 기반 작업 큐가 많다. Kafka도 쓰지만 kafkajs 유지보수 상태를 확인해야 한다.

### 요약
- Kafka: 대용량 이벤트 스트리밍, 데이터 파이프라인, 대규모 MSA의 표준에 가깝다.
- RabbitMQ: 작업 큐와 복잡한 라우팅이 필요한 곳에서 여전히 많이 쓴다.
- Redis Streams: 이미 Redis가 있고 규모가 크지 않을 때 가볍게 쓴다.
- 이번 벤치마크 결과(Kafka가 대량 처리와 높은 동시성에서 앞섬)는 업계 쓰임새와 방향이 맞다. 다만 Kafka가 많이 선택되는 가장 큰 이유는 속도 하나가 아니라 메시지 보관, 재처리, 생태계다.
