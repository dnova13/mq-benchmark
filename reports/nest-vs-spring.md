# Nest vs Spring 비교 결과

- 측정일: 2026-10-09
- 방법: 두 앱 모두 시나리오 10개 × MQ 3개 × 5회 반복(워밍업 1회 제외)의 중앙값, 총 150회씩. 미완료 0회
- 같은 머신, 같은 브로커와 DB, 같은 부하 도구(k6, curl), 한 번에 한 앱만 실행
- Nest는 `npm run build` 후 `node dist/main.js`로 실행했고, Spring은 `java -jar`로 실행했다.
- 원본: `reports/nest-raw.jsonl`, `reports/spring-raw.jsonl` / 앱별 상세 표: `reports/nest-tables.md`, `reports/spring-tables.md`
- Spring 단독 결과와 결론: `reports/spring-result.md`

## 결론 먼저

1. **전체적으로 Nest와 Spring 중 어느 쪽이 더 빠르다고 말하기 어렵다.** 30개 케이스(시나리오 10 × MQ 3) 중 21개는 5회 측정의 최소~최대 범위가 겹쳐서 우열을 가릴 수 없었다. 범위가 겹치지 않은 9개 중 Spring이 4개, Nest가 5개 앞섰다.
2. **"Spring이 더 낫다"는 가설은 이번 측정에서 뒷받침되지 않았다.** 전체 기하평균 비율은 Nest/Spring = 1.09로 Nest가 약간 높았다. 다만 이 차이는 특정 케이스(Redis, DB 없음 시나리오)에 몰려 있다.
3. **차이가 나는 곳은 MQ와 클라이언트 조합에 따라 갈렸다.**
   - Redis Streams: Nest가 크게 앞섰다. (A2: 169,492 vs 32,573 TPS, 5.2배)
   - Kafka: Spring이 앞선 케이스가 더 많았다. (B2 0.67, B3 0.42, A3 0.71, A5 0.74)
   - RabbitMQ: 대부분 범위가 겹쳐 차이가 없었다.
4. **MQ 순위가 앱에 따라 뒤집혔다.** Spring에서는 Kafka가 10개 중 8개에서 1위였고, Nest에서는 Redis가 7개에서 1위, Kafka는 2개에 그쳤다. 즉 "MQ 자체의 성능"과 "그 MQ를 쓰는 클라이언트 라이브러리와 구현 방식의 성능"을 분리해서 봐야 한다.
5. **DB 저장이 들어가면 앱 차이가 거의 사라진다.** DB 포함 21개 케이스의 비율은 0.98이고, DB 없는 케이스는 1.38이다. DB 풀(10)이 병목이라 앱과 MQ 차이가 가려진다.
6. **I/O 중심 작업에서 Node가 불리하지 않다**는 일반론과 방향이 맞다. 이 벤치마크의 컨슈머는 CPU 연산이 거의 없고 대부분 I/O 대기이기 때문이다. CPU 작업이 늘었을 때의 결과는 측정하지 않았다.

## 해석

- **Redis에서 Nest가 크게 앞선 이유 (추정):** 두 앱의 구현 방식이 같지 않다. Nest는 ioredis 파이프라인으로 발행하고, 컨슈머는 워커 10개가 한 번에 최대 100건을 읽어 `Promise.all`로 병렬 처리한 뒤 한 번에 ack한다. Spring은 컨슈머 10명이 메시지를 하나씩 순차 처리하고 건마다 ack한다. 이 구현 차이가 런타임 차이보다 클 가능성이 높다. 같은 구현 방식으로 맞춰서 다시 재야 확정할 수 있다.
- **Kafka에서 Spring이 앞선 이유 (추정):** Nest는 kafkajs의 `eachBatch`로 배치를 병렬 처리하고, Spring은 `@KafkaListener`로 파티션 10개에 스레드 10개를 붙여 처리한다. B3(DB 없음, 요청당 1건)에서 Spring이 2.4배 빨랐다. 요청 1건마다 `send` 한 번을 하는 구조에서 kafkajs 프로듀서의 오버헤드가 드러났을 수 있다. 이 역시 추정이다.
- **DB 없는 시나리오에서 Nest의 TPS 편차**가 크다. 예를 들어 A2 RabbitMQ는 17,007~37,313이다. 중앙값만 보지 말고 범위를 같이 본다.
- **지연(p95):** DB 없는 단건 시나리오 B3에서 Redis는 Nest 7ms, Spring 317ms였다. Spring의 Redis 컨슈머가 건별 처리와 건별 ack를 하는 구조와 관련이 있어 보인다.

## 한계

- 이 비교는 **"Nest로 구현한 것 vs Spring으로 구현한 것"**이다. 런타임만의 순수 비교가 아니다. 위처럼 컨슈머 처리 방식(배치 병렬 vs 건별)이 다르다.
- 단일 머신에서 앱, 브로커, DB, 부하 도구가 자원을 나눠 쓴다. 절대 수치보다 상대 비교로만 쓴다.
- 발행 확인(RabbitMQ confirm 등)과 MQ 튜닝은 하지 않았다.
- 최대 10,000건이다. 장시간, 대량 처리와 안정성은 측정하지 않았다.
- 각 케이스는 5회 측정이라 통계적 유의성 검정을 한 것이 아니다. 범위 겹침으로 대략 판단했다.
- CPU 연산이 큰 작업(예: 메시지당 해시 반복)은 측정하지 않았다. 그 경우 결과가 달라질 수 있다.

## 다음에 확인하면 좋은 것

| 항목 | 목적 |
|---|---|
| 컨슈머 처리 방식을 같게 맞추기(예: Spring도 배치 병렬 처리, 또는 Nest도 건별 처리) | 런타임 차이와 구현 차이 분리 |
| 메시지당 CPU 작업 옵션(`cpu=N`) | CPU 중심에서 Nest와 Spring 차이 확인 |
| Spring 가상 스레드(`spring.threads.virtual.enabled=true`) | 블로킹 I/O 약점 완화 효과 |
| 100,000건 이상 시나리오 | 장시간 처리량과 순위 유지 여부 |
| RabbitMQ publisher confirm 켜기 | 내구성 조건을 맞춘 비교 |
